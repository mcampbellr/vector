Detect the cards that **lie** — a card still in `review` whose PR is already merged, a card in
`review` with no trace of code, a closed Jira ticket behind an open card, an OpenSpec change no card
tracks. The binary sweeps deterministically (git/gh included); Jira is read only through the
connected MCP from this command; the prose is generated by a cheap agent. **You never write
Vector's state yourself** — every remediation is an existing primitive (`vector spec pr|close|status`,
`vector sync`), applied only after explicit per-batch confirmation (CLI-owns-writes).

**Input**: `$ARGUMENTS` (optional flags): `--skip-jira` (never contact the Jira MCP) and `--fix`
(offer the fix-eligible remediations, one confirmation per drift type). Both may be combined;
neither is required. Without `--fix` the command is strictly read-only.

> Token routing: the sweep is free (binary, zero LLM; `git`/`gh` subprocesses only), the Jira reads
> are bounded MCP calls, and the prose is cheap structured work → the **Haiku**
> `vector-check-reporter` agent (`product/token-routing.md`). The binary never calls an LLM and
> never contacts Jira.

## Hard rules

- **Read-only without `--fix`.** `vector check` never writes `.vector/`; the Jira reads are
  read-only. Nothing is mutated unless `--fix` is passed **and** the user confirms a batch.
- **The binary never contacts Jira.** Jira is read here, through the MCP connected in this session.
  `--skip-jira` → never invoke the MCP, however many specs carry a ticket.
- **Never apply without confirmation.** There is no "apply everything" path, with any flag
  combination. One `AskUserQuestion` per drift type — never one question mixing types.
- **Only existing primitives.** Every fix is the discrepancy's own `suggestion` (or `vector sync`).
  Never invent a write primitive, never edit `.vector/` by hand, never move a Jira ticket.
- **Report-only types are never offered as fixes**: `pr-closed-unmerged`,
  `review-with-pending-tasks`, `branch-without-pr` (its `/vector:ship <id>` suggestion is for the
  user to run), `broken-ticket-link`, and every discrepancy with `fixEligible: false`.

## 1. Run the sweep

```bash
REPORT=$(vector check --json --repo-root "$REPO_ROOT")
```

Warnings on stderr name each degradation (no `gh`, `git fetch origin <base>` failed, not a git
repo, no `.vector/config.json`) and which checks were skipped — relay them to the user verbatim;
they are not errors. The JSON:

```json
{
  "generatedAt": "…",
  "language": "es",
  "specs": [ { "id": "…", "title": "…", "status": "review", "ticket": { "provider": "jira", "key": "ACME-1", "url": "…", "auto": false } } ],
  "discrepancies": [ { "specId": "…", "type": "…", "severity": "high|medium|low", "description": "…", "suggestion": "…", "fixEligible": true } ],
  "notes": [ { "specId": "…", "description": "…" } ]
}
```

- `specs[]` holds only the non-archived specs carrying a well-formed ticket (step 2's input).
- `discrepancies[]` carries the binary's 11 drift types: `invalid-state`, `no-ticket`,
  `malformed-ticket-ref`, `merged-but-not-closed`, `review-without-code`,
  `review-with-uncommitted-work`, `pr-closed-unmerged`, `review-with-pending-tasks`,
  `openspec-change-without-card`, `card-without-change`, `branch-without-pr`.
- `notes[]` are informational (a dirty worktree on an `in-progress` card, an ambiguous PR match,
  a branch already merged without a recorded PR) — never a discrepancy, never fixed.
- `language` (omitted when unset) is the repo's configured prose language.

## 2. Cross-check Jira (skip on `--skip-jira`)

If `--skip-jira` is set, skip this step entirely and go to step 3.

Otherwise, for each `specs[]` entry whose `ticket.provider` is `jira` (other providers are not
cross-checked in V1), read the issue through the Jira MCP, **sequentially**, and append the
findings to the **same** `discrepancies` array with the identical shape.

1. **Resolve the read tool from the session's connected MCP.** Use the exact read-issue tool as
   loaded (`mcp__<server>__<tool>`); never assume a dialect. Known dialects, as hints only: official
   Atlassian remote → `mcp__atlassian__getJiraIssue`; community mcp-atlassian →
   `mcp__mcp-atlassian__jira_get_issue`. Pass only the ticket `key` (or `url`) — never credentials.
2. **Degrade, never abort.** No Jira MCP connected, or no session → skip this step, tell the user
   "Jira cross-check skipped — no Jira MCP available", and continue with the binary's findings.
   Never simulate a Jira result.
3. **Classify each read** (at most one Jira discrepancy per spec):
   - **Read fails** (404, invalid key, no permission) → `broken-ticket-link`, `severity: "high"`,
     `fixEligible: false`, `description: "Jira could not resolve <KEY> (<short error>)"`,
     `suggestion: "vector spec link <id> <ticket-ref>"`.
   - **Issue is done** (`statusCategory.key == "done"`) **and** the card is not `closed` →
     `ticket-closed-while-open`, `severity: "high"`,
     `description: "<KEY> is <jiraStatus> in Jira but the card is still <status>"`:
     - card `open` / `in-progress` / `review` → `fixEligible: true`,
       `suggestion: "vector spec close <id> --resolution done"`;
     - card `needs-attention` → `fixEligible: false` (the state machine has no
       `needs-attention → closed`), `suggestion: "vector spec status <id> review && vector spec close <id> --resolution done"`.
   - Anything else → no discrepancy.

## 3. Generate the report (Haiku)

Pass the **combined** JSON (the binary's report with the Jira discrepancies appended) to the
`vector-check-reporter` subagent (model: Haiku). Do not write the prose yourself. If `language` is
present, prepend `Write the prose in: <language>` above the pasted JSON; otherwise add no
directive (the agent falls back to the conversation language). It returns:

```json
{ "summary": "<one short paragraph>", "bySeverity": { "high": [ … ], "medium": [ … ], "low": [ … ] }, "notes": [ "…" ] }
```

### 3a. Validate the report (shape-gate)

Valid = parseable JSON; `summary` a non-empty string; `bySeverity` with `high`/`medium`/`low`
arrays; every entry's `id`/`type`/`command` equal to an input discrepancy's
`specId`/`type`/`suggestion` **verbatim**, in the bucket of its input `severity`, each input
discrepancy exactly once.

- **Valid (attempt 1):** go to §4.
- **Invalid (attempt 1):** re-spawn `vector-check-reporter` (same Haiku tier) with the same JSON and
  this directive prepended:
  ```
  The previous attempt returned malformed or invalid JSON.
  Return ONLY a valid JSON object matching exactly:
  {"summary":"<string>","bySeverity":{"high":[…],"medium":[…],"low":[…]},"notes":[…]}
  Never invent a discrepancy; each command is the input suggestion verbatim; group only by the
  input severity. No preface, no code fences, no trailing text.
  ```
  - **Valid (attempt 2):** go to §4.
  - **Invalid (attempt 2):** print the combined report grouped by severity yourself from the raw
    JSON (no prose) and note `report prose skipped: subagent returned invalid JSON twice`.

## 4. Print the report

Print `summary`, then the buckets High → Medium → Low: per entry, the spec id (plus `ticketKey`
when present), the `type`, and the exact `command` as a copy-pasteable code span. Then the notes,
labelled informational. No discrepancies → "no discrepancies found" plus how many specs were
checked. Without `--fix`, end here (go to §6).

## 5. Apply fixes (only on `--fix`)

1. **Group** the combined `discrepancies` with `fixEligible: true` by `type`. Never include a
   report-only type (see Hard rules). No eligible items → say so and go to §6.
2. **Before each batch, re-read the board** (`vector spec list --json --repo-root "$REPO_ROOT"`) and
   drop items whose card already reached the target state (e.g. already `closed` for a close fix,
   already `in-progress` for `review-with-uncommitted-work`) — count them as `skipped (already
   applied)`. This keeps a re-run after a Ctrl+C mid-batch safe.
3. **One `AskUserQuestion` per remaining type**, showing the exact plan — every affected id with the
   command that will run — and these options:
   - **Apply the whole batch** (list the N commands);
   - **Review item by item** → then one `AskUserQuestion` per item (apply / skip);
   - **Skip this type** → nothing in this type is applied; continue with the next type.
4. **Apply sequentially** each confirmed item by running its `suggestion` verbatim with
   `--repo-root "$REPO_ROOT"` appended to every `vector` invocation in it. Exception:
   `openspec-change-without-card` is fixed by running `vector sync --repo-root "$REPO_ROOT"`
   **once** for the whole confirmed batch (sync is additive and idempotent).
5. **A failure never stops the batch.** If a primitive rejects (e.g. an illegal transition because
   the card moved since the sweep), record its error for that id and continue.
6. **Final tally**: applied / failed (with each error) / skipped. Suggest re-running
   `/vector:check` to confirm the drift went down.

## 6. Report

One or two lines (in `language` when set, else the conversation language): totals by severity,
number of notes, whether Jira was cross-checked or skipped (and why), any degradation warnings,
and — with `--fix` — the applied/failed/skipped tally.

## Notes

- **Severity and fix-eligibility are fixed by the binary (and by §2 for Jira types)** — the
  reporter only groups; it never re-judges.
- **Matching cascade (binary):** the PR recorded on the card → the exact branch
  `<branchPrefix><id>` → `gh pr list --state all` by id. More than one candidate → an ambiguity
  note, never a fix. `git fetch origin <base>` runs once before any merge/ancestry assertion; if it
  fails, only the fresh-ref checks are skipped.
- **`review-with-pending-tasks`** replaces the silent `review → in-progress` regression
  `vector sync --reconcile` used to apply; moving the card back is a human call
  (`vector spec status <id> in-progress`).
- If `vector` is not found, it isn't installed — tell the user; never edit `.vector/` by hand.
